要理解 HTTP/2 对比 HTTP（通常指 HTTP/1.1，HTTP 协议的主流历史版本）的重大提升，需从 **性能瓶颈解决、协议底层重构、功能扩展** 三个核心维度展开。HTTP/1.1 因设计年代早（1999 年发布），无法适配现代网络中“多资源并发加载、低延迟传输”的需求，而 HTTP/2 正是针对这些痛点进行了颠覆性优化。


### 一、核心提升：解决 HTTP/1.1 的并发性能瓶颈
HTTP/1.1 最致命的问题是 **“串行请求 + 连接限制”**：同一域名下，浏览器默认仅允许 6-8 个 TCP 连接并发，超出的请求需排队（“队头阻塞”，Head-of-Line Blocking）；且每个连接中，请求必须串行发送（前一个请求响应完成后，才能发下一个），导致多资源（如图片、CSS、JS）加载时延迟极高。

HTTP/2 通过 **“二进制帧 + 多路复用”** 彻底解决了这一问题，这是其最核心的提升：

| 技术特性                | HTTP/1.1 实现方式                          | HTTP/2 实现方式                          | 效果对比                                                                 |
|-------------------------|-------------------------------------------|-----------------------------------------|--------------------------------------------------------------------------|
| 数据传输单位            | 文本格式（ASCII 编码），易读但解析效率低    | 二进制帧（Binary Frames），不可读但解析快 | 二进制帧体积更小、解析速度提升 30%+，且避免文本格式的歧义（如换行符冲突） |
| 并发请求机制            | 基于 TCP 连接并发（每连接串行请求）        | 基于“流（Stream）”的多路复用             | 1 个 TCP 连接可承载 **无数个流**，每个流对应 1 个请求/响应，流间独立并行 |
| 队头阻塞问题            | 存在（同一连接中，前请求阻塞后请求）       | 不存在（流间独立，某流阻塞不影响其他流） | 多资源加载时，不会因某张图片加载慢导致后续 CSS/JS 排队，页面渲染速度大幅提升 |

**举个例子**：加载一个包含 20 张图片、3 个 CSS、2 个 JS 的页面  
- HTTP/1.1：需建立 3-4 个 TCP 连接（因单域名 6-8 连接限制），每个连接串行处理 5-7 个请求，总延迟 = 连接建立时间 + 串行请求排队时间；  
- HTTP/2：仅需 1 个 TCP 连接，25 个资源通过 25 个独立流并行传输，总延迟 ≈ 单个连接建立时间 + 最慢资源的传输时间。


### 二、关键优化：减少网络往返与资源体积
除了并发问题，HTTP/1.1 的“重复传输”和“无状态开销”也会浪费带宽和延迟，HTTP/2 通过 **头部压缩、服务器推送、流量控制** 进一步优化：

#### 1. 头部压缩（HPACK 算法）
HTTP 请求/响应的“头部（Header）”包含大量重复信息（如 `Host`、`User-Agent`、`Cookie`、`Accept` 等），HTTP/1.1 每次请求都会完整传输这些头部，导致带宽浪费（尤其 Cookie 较大时，头部体积可能占请求的 50% 以上）。

HTTP/2 采用 **HPACK 压缩算法**，通过两种方式减少头部体积：
- **静态字典**：预定义常用头部（如 `:method GET`、`:status 200`），传输时仅用 1-2 字节的“索引”代替完整字符串；
- **动态字典**：记录当前连接中已传输的自定义头部（如 `Cookie: xxx`），后续请求仅需传输“差异部分”或索引。

**效果**：头部体积可压缩至原来的 1/5 ~ 1/10，尤其适合移动端（带宽有限场景）。


#### 2. 服务器推送（Server Push）
HTTP/1.1 是“请求驱动”的：浏览器必须先解析 HTML，发现需要加载 CSS/JS，再发送请求获取这些资源（存在“解析延迟”）。

HTTP/2 支持 **服务器推送**：服务器在响应浏览器的初始请求（如请求 `index.html`）时，可主动“推送”浏览器后续可能需要的资源（如 `style.css`、`app.js`），无需等待浏览器显式请求。

**举个例子**：  
- HTTP/1.1：浏览器 → 请求 HTML → 接收 HTML 并解析 → 发现需要 CSS → 再请求 CSS → 接收 CSS；  
- HTTP/2：浏览器 → 请求 HTML → 服务器同时返回 HTML + 主动推送 CSS → 浏览器直接用推送的 CSS 渲染，减少 1 次网络往返。

**注意**：推送需避免“冗余资源”（如浏览器已缓存 CSS 但服务器仍推送），因此需结合 `Cache-Control` 等机制判断。


#### 3. 精细化流量控制
HTTP/1.1 无流量控制机制：若服务器发送数据过快，可能导致客户端（如手机）缓冲区溢出，或占用过多带宽影响其他应用。

HTTP/2 支持 **基于流的流量控制**：
- 客户端可通过“窗口更新帧”告知服务器：“当前我的缓冲区还能接收 N 字节数据”；
- 服务器需严格按照客户端的窗口大小发送数据，避免拥塞；
- 流量控制可细化到“单个流”（如优先保证 JS 流的带宽，限制图片流），而非 HTTP/1.1 的“整连接控制”。


### 三、其他重要改进：安全性与协议扩展性
#### 1. 强制与 TLS 结合（事实上的标准）
HTTP/2 协议本身未强制要求加密，但所有主流浏览器（Chrome、Firefox、Safari）均只支持 **“基于 TLS 的 HTTP/2”**（即 `HTTPS` 通道），原因是：
- 避免 HTTP/2 被用于“中间人攻击”（如劫持推送资源）；
- 与 HTTPS 共享 TLS 握手过程，减少额外连接开销。

因此，HTTP/2 事实上成为了“加密协议”，安全性比 HTTP/1.1（明文）大幅提升。


#### 2. 协议扩展性更强
HTTP/1.1 基于文本格式，扩展新功能需通过“新增头部字段”（如 `X-XXX`），灵活性低且易冲突；  
HTTP/2 基于二进制帧结构，帧的“类型字段”可轻松扩展新功能（如后续的 HTTP/3 正是基于 HTTP/2 的帧结构演进），无需修改协议核心逻辑。


### 四、HTTP/2 与 HTTP/1.1 核心差异总结
| 对比维度                | HTTP/1.1                                  | HTTP/2                                  |
|-------------------------|-------------------------------------------|-----------------------------------------|
| 数据传输格式            | 文本（ASCII）                             | 二进制帧                                 |
| 并发机制                | 多 TCP 连接 + 串行请求（队头阻塞）        | 单 TCP 连接 + 多路复用（无队头阻塞）     |
| 头部处理                | 无压缩，每次完整传输                      | HPACK 压缩（静态+动态字典）              |
| 服务器能力              | 被动响应请求                              | 支持主动推送资源                        |
| 流量控制                | 无（依赖 TCP 层控制）                     | 基于流的精细化控制                      |
| 安全性                  | 明文传输（可选 HTTPS）                    | 事实上强制 TLS（HTTPS）                 |
| 扩展性                  | 依赖头部扩展，灵活性低                    | 基于帧类型扩展，易扩展                  |


### 延伸：HTTP/2 的局限性与 HTTP/3 的诞生
尽管 HTTP/2 解决了 HTTP/1.1 的大部分问题，但仍存在一个底层瓶颈：**依赖 TCP 协议**。TCP 的“三次握手”延迟、“队头阻塞”（若 TCP 层丢包，整个连接的所有流都会阻塞），在高丢包场景（如 5G/卫星网络）下仍会影响性能。

因此，HTTP/3 进一步将传输层从 TCP 改为 **QUIC 协议**（基于 UDP 实现，自带拥塞控制、0-RTT 握手、丢包不阻塞），但 HTTP/2 仍是当前主流的高性能协议（截至 2024 年，全球约 70% 的网站已支持 HTTP/2）。
